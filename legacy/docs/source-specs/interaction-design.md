## 0. 前置说明

### 0.1 证据等级

| 标记 | 含义 |
|---|---|
| `[已验证]` | 可从三张截图逐像素读出，或来自 Accessibility API 导出的菜单树，或来自已实测的两次按键（`⌘⇧E`、`` ⌃` ``） |
| `[推测]` | 未经实际操作确认。**每一条 `[推测]` 都必须在同一行给出推测依据**，否则视为编造 |

> **本文档的根本约束**：三张截图是同一个静止时刻的三次拍摄，其中
> **没有任何 hover / pressed / focus 态的像素证据**。整个第 2 章的交互状态部分
> **绝大多数是推测**，只有 selected 与 disabled 各有一例实测。凡是推测的，
> 下文一律给出「从哪条实测值外推」或「同类应用的哪条通行做法」。

### 0.2 隐私占位约定

截图里的真实项目名、任务标题、分支名、用户名、终端输出，本文档一律替换为
「项目 A」「任务标题 N」`feature/xxx`、`user@host`、`app/src/FileA.ext`。
mock 的 `src/data.js` 已经是占位数据，引用其中的 `project-alpha` / `Widget.tsx`
等名称是安全的（那是 mock 自己编的示例，不是实测内容）。

### 0.3 mock 审查的快照时点

第 4.4 节的逐元素审查基于 `uiclone/demos/codex/mock/src/` 的一次快照（最后修改约
`2026-07-26 18:37`，14 个组件 / 1672 行）。**该目录正在被另一路改动同时修改**，
若某条结论与当前代码不符，以代码为准，判据本身（4.2 / 4.3）不受影响。

### 1.2 分层判据

分层不是拍脑袋，用五条判据打分。**J1 是否决性的**（不满足直接出局 L1），
J2–J5 用来在剩下的功能之间排序。

| # | 判据 | 问法 | 为什么它能区分核心与边缘 |
|---|---|---|---|
| **J1** | **主路径必经** | 把它删掉，用户还能不能完成「提任务 → 拿改动 → 审阅 → 落地」这条链？ | 这是产品存在的理由。断链的功能一定是核心，锦上添花的一定不是 |
| **J2** | **常驻面积** | 它是否长期占据三栏中的一整栏 / 一整块？ | 界面面积是产品自己投的票。占一整栏 = 产品认为它天天要用 |
| **J3** | **官方登记** | 它是否进了 View 菜单并分到了快捷键？ | 进 View 菜单 = 被官方认定为一级能力；只在 Help / ChatGPT 菜单里 = 外壳功能 |
| **J4** | **证据强度** | 有完整截图 / 有实测 / 只有菜单名？ | **只有菜单名的功能，做出来 100% 是编的**。这条决定「能不能做对」，而不是「该不该做」 |
| **J5** | **辨识信息量** | 做了它之后，观众能否一眼认出「这是 Codex，不是普通聊天窗」？ | 复刻的价值在于传达产品特征，不在于控件数量 |

### 1.3 L1 核心主线（必须做）

L1 = 满足 J1，且 J4 证据充分。共 **7 项**，构成一条闭环：

| 序 | 环节 | 承载功能 | 界面位置 | 缺了会怎样 |
|---|---|---|---|---|
| ① | **选会话 / 开会话** | F01 + F02 | 左栏 | 无法在多任务之间切换，Codex 退化成单窗口聊天 |
| ② | **下达任务** | F11 输入框 | 中栏底部 | 无法开启新一轮，界面变成只读回放 |
| ③ | **读结果** | F05 正文 + F06 过程折叠条 | 中栏 | 不知道 agent 做了什么 |
| ④ | **看改动汇总** | F08 Edited files 卡片 | 中栏 | 不知道改了哪些文件、改了多少 |
| ⑤ | **审 diff** | F13 + F14 Review 面板 | 右栏 | **这是 Codex 与普通聊天的分界线**，缺了就只剩聊天 |
| ⑥ | **落地** | F09 commit / push | 中栏（右对齐块） | 改动无法进入仓库，闭环断在最后一步 |
| ⑦ | **确认落地结果** | F10 分支名 + PR 链接 | 中栏 | 用户不知道推到哪去了、怎么开 PR |

### 1.4 L2 辅助功能（应该做）

L2 = 不在主路径上，但 **J2 面积大**或 **J3/J4 证据硬**，缺了会让界面「结构不对」。

| 功能 | 为什么应该做 | 做到什么程度 |
|---|---|---|
| F12 标签页容器 | **这是全应用统一的信息架构**：右侧面板与终端面板用的是同一套「胶囊标签 + 内嵌 × + 尾部 `+`」。不做标签，右栏就变成一个固定视图，`⌘⇧E` 的实测行为（新建标签而非切换视图）也无从表达 | 完整：新建 / 切换 / 关闭 / 关到 0 的空态 |
| F15 文件树 + Open file | `⌘⇧E` 是**仅有的两次实测交互之一**，证据最硬；文件树占右栏 249pt 宽 | 完整：过滤框可输入、空结果态、目录/文件两段排列、彩色类型图标 |
| F16 终端 | `` ⌃` `` 是另一次实测；且它的**挤压式布局**（中栏输入框上移 280pt、右栏截断）是本应用最容易做错的布局特征 | 完整：多标签、面板级 × 与标签级 × 分离、挤压不覆盖 |
| F17 三个面板开关 | **唯一实测到的交互状态证据**（按钮 2 的底色在 `` ⌃` `` 前后变化）就在这里 | 完整：三个开关 + 激活态 `#F3F3F3` 底 |
| F02 New chat | 是「空会话」状态的唯一入口，第 3 章的状态机需要它 | 至少：切到空会话态 |
| F07 消息操作行 | 面积小但**每条消息都有**，缺了消息就没有下边界 | 静态渲染即可；只有「复制」值得做成真交互 |
| F18 中栏头部 | 承载会话标题，是「切换会话」这件事的视觉反馈落点 | 标题跟随会话变化；其余控件建议降级为不可点（见 4.4） |

### 1.5 L3 边缘功能（可以不做）及理由

**不做的理由分四类**，理由必须写清楚，否则「不做」就变成了偷懒：

| 理由类型 | 含义 | 功能 |
|---|---|---|
| **(a) 零视觉证据 —— 做了就是编造** | 只有菜单项名或一个图标位置，没有任何形态截图。J4 一票否决 | F20 内置浏览器（占 View 菜单三项的大功能，但**一张图都没有**）、F21 Pinned Summary（与中栏头部大纲图标的对应关系纯属推测）、F22 搜索面板、F23「Codex ⌄」下拉内容 |
| **(b) 不属于 Codex 工作区语义** | 是 ChatGPT 应用外壳，不是 Codex 这个工作区的能力 | F24 账户菜单 / Settings / Check for Updates / Log Out |
| **(c) 无状态产出** | 触发后界面没有可复刻的新形态，做了也看不出来 | F25 缩放（`⌘+/-/0`）、New Window、Close；F03/F04 会话导航与前进后退（在单页 mock 里退化为无操作） |
| **(d) 可能根本不存在** | 是「同类产品有，但这个产品的截图里没有」的功能，做了会误导 | diff 逐行评论、hunk 级「接受 / 拒绝」按钮（截图中未见任何行内按钮）、diff 内直接编辑 |

> **补充说明 (a)**：`Reload Browser Page ⌘R` 在导出菜单树的那一刻是 `enabled: false`，
> 而 View 菜单其余项均为 enabled —— 这是「浏览器标签页确实存在且当时没打开」的
> `[已验证]` 间接证据。但**知道它存在 ≠ 知道它长什么样**。J4 关心的是后者。
>
> **F19 `Open Folder… ⌘O`** 归入 L3 属于边界情况：它是 File 菜单里的正式能力，
> 且很可能就是侧栏项目分组的来源，但它触发的是**系统文件选择器**（macOS 原生面板），
> 不产生应用内可复刻的形态。属于 (c)。

### 1.6 主路径核对结论

任务描述里给的草案是「任务会话管理 → 查看改动 → 审阅 diff → 提交推送」。
核对三张截图与菜单树后，**准确版本是 7 段闭环，而不是 4 段线性**，两处差异：

| 差异 | 说明 | 证据 |
|---|---|---|
| **首端漏了「下达任务」** | 输入框（485 × 99，贴着中栏底部固定）是主路径的起点。草案从「会话管理」直接跳到「查看改动」，跳过了产生改动的动作 | `[已验证]` 输入框在两种状态下都存在且高度恒定 99 |

### 2.2 全局交互状态令牌与外推链

#### 2.2.1 从三例 selected 反推出「选中态是半透明叠加层」

| 位置 | 实测选中色 | 周围底色 | 相对底色的黑度 |
|---|---|---|---|
| 激活标签页 / 激活面板开关 / commit / push | `#F3F3F3` | `#FFFFFF` | ≈ **4.7% 黑** |
| 侧栏当前条目 | `#E8E5E4` | `#EAE9E9`（毛玻璃） | ≈ **2% 黑**，且偏暖 |

**`[推测]` 结论**：选中态不是两个硬编码 hex，而是**同一层半透明中性叠加**（约 4–5% 黑）。
落在毛玻璃侧栏上时，因为底层本身带透明与模糊，实测差值被压缩到 2% 并被桌面壁纸染暖。
**推测依据**：同一个设计系统不会给「选中」这一个语义配两个不相干的颜色；
且 features.md 已实测确认侧栏底色本身自上而下有渐变（`#F2EFEF → #E5E4E6`），
说明该层确实是半透明合成的结果。
**复刻含义**：写 `rgba(0,0,0,0.045)` 而不是 `#F3F3F3` + `#E8E5E4` 两个常量。

#### 2.2.2 六个交互状态的令牌表

| 状态 | 视觉规格 | 证据 | 推测依据 |
|---|---|---|---|
| **default** | 无背景；图标 `#878787`，文字按层级取 `#0D0D0D` / `#616161` | `[已验证]` | — |

#### 2.2.3 状态优先级

`[推测]` 当多个状态同时成立时的叠加规则（依据：CSS 与所有 UI 框架的通行顺序）：

```
disabled  >  active/pressed  >  selected  >  hover  >  default
     └ 禁用时不响应 hover/active，但 selected 的底色保留
focus-visible 与上述任一状态并存（是独立的一层 outline，不是背景色）
```

### 2.7 截断策略：应用里有两种，不要统一成 ellipsis

### 3.3 侧栏条目的状态标记：一个必须解决的歧义

`[已验证]` 截图中，**当前选中的那一条**任务条目在高亮块右内侧有一个**紫色的分支 / merge 图标**，
其余条目没有。这一条实测事实有两种互斥解释：

| 解释 | 含义 | 图标应该跟着什么走 | 对 mock 的影响 |
|---|---|---|---|
| **A. 选中态装饰** | 它是 selected 态的一部分 | 跟着高亮走 | 切换会话时图标跟着高亮移动 |
| **B. 会话状态指示** | 它标记「该会话已产生分支 / PR」，即 S5 | 跟着**会话状态**走 | 多个会话可以同时有图标；当前会话若是 S0/S3 则**不应该**有 |

**`[推测]` 判断：B 更可能。** 三条依据：
1. 图标形状是 **git 分支 / merge**，语义指向仓库状态，与「被选中」无关；
2. 若是选中装饰，用一个彩色（紫）图标去装饰一个用 2% 中性灰表达的选中态，
   在视觉层级上不成比例——该应用的选中态一贯是「加中性底、前景不变」；
3. 恰好当前选中的会话就是 S5（已推送），**两种解释在这一张截图上不可区分**——
   这正是它成为歧义的原因。

> **对 mock 的直接影响**：当前 `TaskList.jsx` 的写法是 `{selected && <TaskBranch/>}`，
> 即采用了解释 A —— 把一个**状态指示器**做成了**选中装饰**。按解释 B 应改为
> `{task.state === 'pushed' && <TaskBranch/>}`，这样侧栏才真正承载了 3.2 表格里的信息。
> 这也是「让 session 列表项的点击变得有意义」的关键一环（见 4.4.3）。

「做完整」的成本可以量化。下表是把 3.2 落地所需的内容清单：

| 状态 | 需要新增的数据 | 成本 | 建议 |

| S5 pushed | **已有**（mock 的 `CHAT` 就是 S5） | 0 | 保留为默认会话 |

| S7 failed | 一段错误文案 | 低 | 建议做 |
| S4 committed | 一行 commit 结果文案 | 低 | 建议做 |

| S2 awaiting | 一个待确认卡片组件 | 中 | 可选 |

> **关键结论**：S3 / S4 / S5 三态可以**共用同一份会话数据**，只是渲染到不同的截断点。
> 也就是说，从「只有 S5」扩到「S0/S3/S4/S5/S6 五态」，**新增内容不超过 3 小段文案**。
> 这直接推翻了「做多状态成本太高」的直觉——真正贵的是给 13 个会话各配一套内容（见 4.4.3）。

## 4. 「可交互元素是否有意义」的判据

### 4.1 问题的准确表述

现象：mock 左侧栏有十余个 session 列表项都可点，点下去只换高亮、右边内容不变。

**这被判定为噪音，但要说清楚噪音的成因不是「点了没用」，而是「看起来能点」。**

| 环节 | 描述 |
|---|---|
| 元素**声称**可交互 | `<button>` + `cursor: pointer` + hover 底色 + Tab 可达 |
| 用户据此**建立预期** | 「点它会切换到那个会话」 |
| 实际**兑付** | 高亮移动了，中栏标题变了，**但正文、卡片、diff 全都没变** |
| 结果 | 预期落空。而且比「不可点」更糟——**不可点只是少了一个功能，兑付不了的可点是在撒谎** |

所以判据的目标不是「让更多元素可点」，而是**让「可点」这个信号是可信的**。
降级（把点不动的东西变成明确不可点）与补内容，是同等合法的两种修法。

### 4.2 七条判据

| # | 判据 | 检查方法 | 不合格时的处理 |
|---|---|---|---|
| **C1** | **因果可见**——点击后必须在**当前视口内**产生变化，且变化**不止于元素自身的外观** | 遮住被点元素本身，界面还有没有别的地方变？ | 降级为不可点，或补一个消费者 |
| **C2** | **状态有消费者**——它改变的状态，必须被至少一个**其它组件**读取并渲染。只被自己读的状态是死状态 | 在代码里搜这个 state，数消费者数量；`< 2` 就要警惕 | 同上 |
| **C3** | **目标态有证据**——交互后的形态必须有截图 / 实测 / 菜单证据；纯推测的形态可以做，但必须在文档或界面上**标注为推测** | 对照第 1 章 F 表的证据列 | 降级为不可点；或做但标注 |
| **C4** | **内容供给相称**——一个元素若有 N 个可能的目标态，就需要 N 份内容。准备不出 N 份，就**收敛可交互实例的数量**，而不是让 N 个实例共享 1 份内容 | 数目标态数量 vs 数据文件里的份数 | 只让 2–3 个实例可交互，其余降级 |
| **C5** | **可逆或有终态兜底**——mock 里的交互应可逆（开→关→开）；不可逆的破坏性动作要么做成可逆，要么保证终态不是死界面 | 反复触发 5 次，界面能否回到初始 | 加兜底空态 + 重建入口 |
| **C6** | **无死点击**——任何带 `<button>` / `role="button"` / `cursor:pointer` / hover 底 的元素，点下去必须有反应。做不到就**移除它的可交互语义**（换成 `div`/`span`，去掉 hover、cursor、tabIndex、title），而不是留一个空 `onClick` | 按住 ⌘ 看高亮（见 4.5），逐个点一遍 | **降级**——这比补内容便宜得多，而且不撒谎 |
| **C7** | **语义与键盘一致**——真可交互的必须是真 `<button>` / `<a>`，能 Tab 到、能回车触发、带 `aria-label` / `aria-pressed` / `aria-expanded`；反过来不可交互的不要挂 `role="button"`；**可聚焦元素不要嵌套** | Tab 走一遍全界面，看焦点顺序是否合理 | 补语义 / 拆嵌套 |

### 4.3 判定决策树

```
对界面上任一「看起来能点」的元素，依次问：

这个元素点下去会改变什么？
├─ 什么都不改 ───────────────────────────────→ 【降级】去掉可交互语义 (C6)
└─ 改变了某个状态 S
   ├─ S 只被它自己渲染 ────────────────────────→ 【降级】或补一个消费者 (C2)
   └─ S 被别的组件渲染
      ├─ 目标态零证据（第 1 章 J4 判为 ✗）──────→ 【降级】或做但标注推测 (C3)
      └─ 目标态有证据
         ├─ 需要 N 份内容但只有 1 份 ────────────→ 【收敛】只留 2–3 个实例可点 (C4)
         └─ 内容齐备
            ├─ 不可逆且会走进死界面 ─────────────→ 【加兜底】空态 + 重建入口 (C5)
            └─ 可逆 ────────────────────────→ 【合格】补齐 6 个交互态 + 键盘可达 (2.3 / C7)
```

| 方案 | 做法 | 成本 | 评价 |
|---|---|---|---|
| **A. 补齐** | 给 13 个会话各配一套对话 + diff | 13 份内容 | ✗ 成本与信息量完全不相称（13 份内容传达的信息 ≈ 1 份） |

> 紫色分支图标就必须跟着状态走（解释 B）而不是跟着高亮走，
> 侧栏才真正开始承载信息，而不只是一个高亮块的跑道。

#### 4.4.4 两处顺带发现的语义问题（C7）

| 问题 | 位置 | 说明 |
|---|---|---|
| **可聚焦元素嵌套** | `RightPanel.jsx` 的 `Tab`、`TerminalPanel.jsx` 的终端标签 | 外层是 `role="button" tabIndex={0}`，内层的关闭 `×` 是真 `<button>` → 嵌套可聚焦元素，Tab 顺序会先停在整个标签、再停在 `×`，是 a11y 反模式。建议外层改用真 `<button>` 并把 `×` 移出其 DOM 子树（用绝对定位叠在胶囊右侧） |
| **外链用了 `<button>`** | `ChatPane.jsx` 的 GitHub 链接 | 链接语义应是 `<a>`；在 mock 里若不真跳转，就该整体降级为不可点文本 |

### 4.5 验收方法：⌘ 高亮就是自查工具

mock 已有一个很好的机制：`store.jsx` 监听 `Meta` 键，给根节点挂 `.cmd-hint`；
`index.css` 用一条选择器把所有 `button` / `a[href]` / `[role=button]` / `input` / `textarea`
描上蓝色 outline。

> **这个功能的真正价值不是给用户看，而是给作者做 C6 自查**：
> 按住 ⌘，界面上亮起的**每一个框都是一次「我能点」的承诺**。
>
> **验收标准**：按住 ⌘ 时亮起的元素集合，应当**恰好等于**第 4.4.1「合格」清单
> 加上第 4.4.3 补完的那几项。当前亮起约 60 个，而只有 ≈18 个兑付得了，
> **差额就是噪音的数量**。P0 降级做完后再按一次 ⌘，亮起的应该只剩 30 出头；
> 全部补完后每一个亮起的框都点得动。

这条验收方法可以推广到任何 UI mock：**给 mock 加一个"高亮所有声称可交互元素"的开关，
然后逐个点一遍。点不动的，要么补内容，要么降级。**
